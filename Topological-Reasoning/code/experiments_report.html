Architecture du code

Chaque script d'expérimentation délègue l'inférence au moteur central via run_eval_osm_gpu.py.

⚙️

Moteur principal d'inférence GPU. Charge le modèle, applique l'adaptateur LoRA, boucle d'évaluation, checkpoints atomiques.

🧠

Implémentation des stratégies CoT, ToT, GoT. Accès au KG OSM via Nominatim avec cache local.

🔧

Fine-tuning LoRA avec SFTTrainer (TRL). Construit les prompts, attache les adaptateurs, sauvegarde les poids.

📊

strategies_osm.py

Stratégies de raisonnement

Chaque stratégie enrichit le prompt avec les preuves OSM avant d'appeler le LLM. La différence réside dans le nombre et la structure des appels.

CoT · Chain-of-Thought

Raisonnement en chaîne

Construit un unique prompt avec toutes les preuves OSM (coordonnées, bounding box, hiérarchie) et demande au modèle de raisonner étape par étape. Une seule génération par exemple. Simple et rapide.

ToT · Tree-of-Thought

Raisonnement arborescent

Génère plusieurs hypothèses de prédicats (branches), évalue chacune avec un prompt distinct, puis sélectionne la meilleure via vote ou score de confiance. Plusieurs appels LLM par exemple.

GoT · Graph-of-Thought

Raisonnement en graphe

Décompose le raisonnement en étapes interdépendantes (nœuds) : extraction des preuves → analyse géométrique → comparaison → conclusion. Chaque nœud est une génération LLM distincte.

GeographicKnowledgeGraph

Classe centrale d'accès au KG OSM. La méthode get_neighborhood_details(place) interroge Nominatim pour récupérer coordonnées, type de lieu, bounding box et hiérarchie administrative. Les résultats sont mis en cache dans results/osm_cache.json pour éviter les requêtes répétées.

run_eval_osm_gpu.py

Fonctions du moteur d'inférence

Le moteur central gère le chargement du modèle, les checkpoints et la boucle d'évaluation.

Patches de compatibilité

Appliqués au démarrage avant tout import pour corriger les incompatibilités du serveur.

_TorchvisionStubFinder

torchvision installé mais cassé (_cast_Long manquant). Un MetaPathFinder intercepte tous les imports torchvision.* et retourne des modules vides avec InterpolationMode correct.

torch.accelerator

Manquant dans PyTorch < 2.4. Polyfill ajouté avant l'import de transformers pour éviter AttributeError.

set_submodule

Méthode manquante dans torch.nn.Module avant PyTorch 2.5. Polyfill implémentant la traversée récursive des sous-modules.

supports_quant_method

Bug transformers ≥5.9 : crash quand config.quantization_config=None. La méthode est remplacée par une version qui retourne False si l'entrée est None.

_save_json_atomic(path, data)
Sauvegarde atomique via fichier temporaire + os.replace. Évite la corruption du checkpoint si le processus est interrompu en cours d'écriture. Garantit que le fichier est toujours valide.
_load_checkpoint(ckpt_path)
Charge le checkpoint JSON existant (indices traités + résultats). Retourne un dict vide si absent ou corrompu. Permet la reprise automatique des expérimentations interrompues sans repasser les exemples déjà traités.
evaluate_strategy(strategy, df, output_dir, model_tag)
Boucle d'évaluation principale. Pour chaque exemple non traité : (1) appelle la stratégie → prédicat prédit, (2) compare avec la vérité terrain, (3) sauvegarde le checkpoint. Affiche la précision en temps réel dans la barre tqdm.
gpu_inference_fn(prompt)
Inférence locale GPU. Tokenise avec troncature à max_position_embeddings − max_new_tokens, génère via model.generate() (température 0.1), décode uniquement les tokens nouveaux. Logue la latence du premier appel.
_local_hf_hub_download(repo_id, filename)
Patch PEFT pour adaptateurs locaux. Intercepte les appels à HuggingFace Hub quand repo_id est un chemin absolu local. Cherche le fichier dans le dossier donné et son parent, avec fallback .bin → .safetensors.
finetune_gptoss.py

Script de fine-tuning LoRA

build_training_prompt(row, tokenizer)
Construit un exemple instruction-following complet : système (rôle expert DE-9IM) + entrée (relation vernaculaire + types géométriques) + sortie attendue (raisonnement + prédicat). Format standardisé pour SFTTrainer.
main()
Pipeline complet : charge CSV → construit Dataset HuggingFace → charge GPT-OSS-20B en bf16 → attache LoRA (r=8, alpha=16, cibles : q/v/k/o_proj) → lance SFTTrainer (3 epochs, lr=2e-4, grad_accum=16) → sauvegarde final_adapter/.

Conclusion

Observations principales

Ce que les résultats révèlent sur l'approche optimale.

🏆

GoT + KG Ollama domine

Le modèle base sans fine-tuning avec la stratégie GoT enrichie par KG OSM (Ollama) atteint 74.0% — la meilleure performance toutes configurations confondues.

⚠️

Le fine-tuning seul ne suffit pas

Les modèles fine-tunés ne surpassent pas systématiquement le modèle base. L'adaptateur topo améliore GoT (61.5%) mais dégrade CoT (53.1% vs 57.3%).

📈

GoT > CoT > ToT en général

La stratégie Graph-of-Thought bénéficie le plus du KG OSM. ToT est systématiquement la stratégie la moins efficace sur ce type de tâche.

🗺️

within & disjoint : prédits facilement

Le modèle base atteint 100% sur within en CoT. crosses et overlaps restent les prédicats les plus difficiles à prédire.
